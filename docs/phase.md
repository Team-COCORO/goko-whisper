# 実装 Phase

段階の順はこの文書だけを見る。画面の契約は `frontend.md`、発行・消込・上限は `backend.md`。企画の前提は `implementation.md`。

いまあるのは、ダーク紫のフロントだけである。名前のあと 800ms で①②ゴールへ自動進行し、4桁はブラウザが作る。`localStorage`、URL スタンプ、バックエンドはない。

```text
[Phase 1] クライアントの進行（URL クエリ × localStorage）
    │
[Phase 2] Workers + D1（発行・消込・上限・残数）
    │
 ★ プレリリース 1 … 導線と受付操作。見た目はいまのダーク紫
    │
[Phase 3] 地図と明治レトロ（ダミー SVG）
    │
[Phase 4] PWA・食品・プレゼント
    │
 ★ プレリリース 2 … 操作感、導線、オフライン、SVG の座標系
    │
[Final] 本番 SVG、印刷用 QR、現地リハーサル
```

プレリリースのホストと本番ホストは別でよい。どちらのホストでも、ページと `/api` は同じオリジンにする。来場者向け QR のホストは、その QR を書き出す前に固定する。

---

## Phase 1 — クライアントの進行

自動進行を外し、標準カメラが開く URL でスタンプを残す。API はまだ呼ばない。

- `AppContext` が `goko-whisper` を `localStorage` と同期する。`clientId`、ニックネーム、二つのスタンプ、`redeemed`、`rewardCode`、`issuedAt`。画面名は保存しない
- `?stamp=spot1|spot2|spot3&token=` を `POST /api/stamp/verify` で Worker の `STAMP_TOKEN` と照合できたときだけフラグを立て、`replaceState` で `stamp` と `token` を消す
- 画面はフラグから決める。初めて付いた囁きだけ再生する。片方だけなら案内に留まる。両方揃い名前が空なら、発行の前に名前を取る
- 「声を刻む」、`startHomeAutoFlow`、戻る操作でのリセットは削除する
- ゴールは未接続のまま、コード欄は空か「準備中」でよい。乱数の `generateCode()` は残さない

食品タブとプレゼントタブは、いまの文言のままにする。配色はダーク紫のままにする。

---



## Phase 2 — 発行・消込・上限

`backend/` の Worker が D1（バインディング名 `DB`）と、ビルド済みフロントを同じホストで配信する。

- `POST /api/token/issue` … `{ nickname, clientId }`。同じ `clientId` には同じ4桁。上限は発行件数。超えそうな挿入は `INSERT … SELECT` の一文で止める。初期値は 100。当日の数は D1 の `UPDATE` で変える
- `POST /api/token/verify` … `{ code, pin }`。PIN は数字 4 桁。消込済みへの再送は `already_redeemed` を成功として返す
- `GET /api/admin/summary` … 発行数、消込数、残数、上限。`Authorization: Bearer` が必要
- フロントは、両方のスタンプと名前が揃い未発行のときだけ発行する。通信失敗時にその場の乱数で埋めない。5分は `issuedAt` からの演出で、過ぎたら「コードを再表示」で同じコードを出す
- 消込は参加者の画面で、PIN のあと真鍮レバーの代わりに、Phase 2 では操作できるスライダーでよい。見た目の作り込みは Phase 3
- `#admin` で残数を見る。トークンは `sessionStorage`。クエリには付けない

秘密は `backend/.dev.vars` と Worker の secret。スタンプ用トークンは `frontend/.env.local`。リポジトリには置かない。

### プレリリース 1

企画と受付リーダーに、公開した Worker の URL を触ってもらう。器はいまのトップ、囁き、ゴールである。「次のデモで地図と配色が変わる。今日決めるのは進み方と受付」と先に伝える。

1. 紙のテスト QR（`spot1` と `spot2`、開発用トークン付き）を標準カメラで読み、スタンプが付く。②が先でも案内が崩れない
2. 4桁、5分後の再表示、PIN とスライド、使用済みの再スライド
3. `reward_limit` を 3 にした終了画面。既にコードを持つ端末は引換できる
4. `#admin` の発行数・消込数・残数
5. スタッフ向け手順の記載方針

ここで合意するのは状態の進み方と受付操作である。地図、明治レトロ、印刷用 QR の GO は取らない。

---



## Phase 3 — 地図と明治レトロ

ホームを全画面マップとボトムシートに載せ替える。Phase 1 の状態遷移はそのまま使う。配色を羊皮紙、赤レンガ、真鍮、藍色へ切り替える。プレリリース 1 のダーク紫はここで終わる。

- `public/maps/dummy-campus.svg`。`viewBox="0 0 2000 2000"`。点灯用に `id="building-goko"` をこの段階から置く
- パンとピンチは DOM の `transform` を直接書く。React state には選択中のピンとシートの開きだけを置く。ズームは 1〜4 倍。ピンは子要素で `scale(1/zoom)`
- シートは羊皮紙。ナビは藍色と線画（羅針盤、ランタン、記念バッジ）。ゴールは入場券の二重枠。レバーは真鍮。未達ピンは真鍮のコイン、達成後は封蝋に朱肉
- 地図と写真だけ `contrast(95%) sepia(10%)`。本文には掛けない
- シートの初期値は、見えている高さ約 18%、半開き約 45%。実機で変えてよい
- ピンのパーセントは仮位置。本番イラストのあとで合わせる

点灯アニメーションの中身は Final まで決めない。

---



## Phase 4 — PWA・食品・プレゼント

当日の 2 回目以降と、模擬店・特典の導線を足す。マップの操作は Phase 3 のままである。

- `vite-plugin-pwa` で JS、CSS、HTML、アイコン、ダミー SVG、掲載画像を事前キャッシュ（Cache First）。`/api` の POST はキャッシュしない
- ホーム画面への追加は案内しない。確認は「一度開いてから機内モードで再読み込み」
- 食品カードは `{ id, name, image, x, y }`。タップでそのピンへズームする。写真が無くてもダミーカードを 1 件以上置く
- プレゼントはバルーンとしおりの紹介。種類はサーバーへ送らない。2 スタンプ後はここからゴールへ進める
- 画像は `frontend/public/images/` の WebP または AVIF。失敗時は「画像なし」



### プレリリース 2

企画、デザイン、全体運営に、本番と同じ機能の画面を触ってもらう。地図だけダミー SVG である。

1. 拡大縮小、ドラッグ、ボトムシートにカクつきがない
2. 模擬店カードからピンへ飛ぶ。囁きが読める
3. 機内モードでも、一度開いた端末で地図とスタンプ帳が動く。発行と消込は「通信が必要」と出る
4. デザインには、ダミーと同じ `viewBox` と `id="building-goko"` で本番 SVG を作れば動く、と渡す
5. デザイン QR（誤り訂正 H、深色×生成り、角丸、五高マーク）の見た目の方向

印刷の GO は出さない。URL に載せる本番ホストと本番トークンが固定され、実寸を標準カメラで読めたあとが Final である。

---



## Final — 本番の地図と現地

- `campus-map.svg` に差し替える。`viewBox` と `id="building-goko"` は維持し、点灯の CSS を付ける。ピンのパーセントを最終調整する
- Service Worker の revision を上げ、ダミーをキャッシュした端末が新しい地図を取るところまで見る。イベント当日中の SW 更新は出さない
- デザイン QR を実寸印刷し、iOS と Android の標準カメラで読む。成功してから看板とチラシの印刷に進む
- 五高記念館の受付と模擬店エリアで、読み取りから消込までを実機で通す。シフトのスタッフに来場者のスマホをスライドしてもらう

---



## どの段階でも変えないこと

- アカウントは作らない。スタンプは端末の `localStorage`。アプリ内カメラは作らない
- コードに失効時刻は持たない。5分で受け取れなくならない
- バルーンとしおりは受付で選ぶ。サーバーは特典 1 枠として数える
- 既にコードを持つ端末は、上限のあとでも消込できる
- ストレージを消した端末は新しい参加者になり、在庫をもう一枠使う
